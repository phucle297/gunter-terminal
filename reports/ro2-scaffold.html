Why this structure?

The crates/ subdirectory convention places all workspace members under a single directory, matching the SPEC.md layout exactly. This avoids top-level clutter as the codebase grows and makes members = ["crates/*"] glob-expansion trivial if needed later.

workspace.dependencies Pattern

All shared external dependencies are declared once in [workspace.dependencies] in the workspace root Cargo.toml. Individual crates inherit them with { workspace = true }. This enforces a single version of every shared dep across all crates — no version skew, no duplicate resolution conflicts when adding crates that both use e.g. serde.

Notable Decisions

crates/ subdirectory matches SPEC layout exactly

The SPEC.md specifies gunter/crates/.... Using the same directory name means any future engineer reading the spec can find the crates exactly where expected. No creative remapping.

gunter-renderer has empty [dependencies]

Rather than omitting the [dependencies] section entirely, an explicit empty section is included. This signals intent: the crate exists as a placeholder and will grow, rather than accidentally being treated as dead code.

Cargo.lock committed

For a binary crate (gunter-app), Cargo.lock should be committed. This is the correct default for applications (vs. libraries). Reproducible builds are important here since this targets a specific PTY + VTE version combination on WSL.

toml declared but not yet consumed

toml = "0.8" is in [workspace.dependencies] but no crate declares toml = { workspace = true } yet. It is pre-declared because config parsing (gunter-core) is the next task. This avoids a future PR that only touches the workspace root to add a dep.
