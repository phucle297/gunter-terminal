Why portable-pty

portable-pty abstracts over two very different PTY subsystems with a single Rust API:

  • Linux/macOS: POSIX openpty(3) / forkpty(3)
  • Windows: ConPTY (pseudo-console API added in Windows 10 1809)

gunter-terminal targets both Linux and Windows (via WSL2). Using portable-pty means the same PtySize, CommandBuilder, and reader/writer API compiles on both hosts. No #[cfg(target_os = ...)] branching needed in application code.

What Is NOT in Scope (Phase 1)

  • out-of-scope tokio async runtime — blocking reader.read() is sufficient for Phase 1 headless verification. Async will be needed when the event loop must service both PTY I/O and UI events simultaneously (Phase 2).
  • out-of-scope winit window — Phase 2 opens a native window via winit and drives a render loop.
  • out-of-scope GPU / wgpu renderer — Phase 2 adds a wgpu-based glyph renderer. Phase 1 uses print_grid() stdout dump only.
  • out-of-scope scrollback rendering — Grid stores a VecDeque<Vec<Cell>> scrollback but it is not exposed yet.

What Reviewer Should Check

GridPerformer lifetime (borrow safety)
In the PTY read loop, GridPerformer::new(&mut grid) creates a performer that mutably borrows grid for the duration of that loop iteration. The performer is dropped at the end of the Ok(n) match arm, before the next reader.read() call. Rust's borrow checker enforces this — the code would not compile otherwise. Safe.
wsl.exe in PATH assumption
The main() function calls CommandBuilder::new("wsl.exe"). This assumes WSL2 is installed and wsl.exe is on PATH. On a Linux host without WSL, spawn_command will panic with "spawn failed". For cross-platform headless CI, the spawn should be guarded or the binary should accept the shell path as a CLI argument (future work).
print_grid is a headless verification tool
print_grid() writes raw character grid to stdout. It is not the final renderer. Its purpose is to let a developer observe PTY output state without a GUI window. It will be replaced by the wgpu renderer in Phase 2.
