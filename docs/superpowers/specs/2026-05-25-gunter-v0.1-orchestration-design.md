# Gunter v0.1.0 — Orchestrated TDD Implementation Design

**Date:** 2026-05-25  
**Scope:** Phase 1 only (SPEC.md Phase 1 — WSL shell → grid buffer, headless, no GPU)  
**Version target:** v0.1.0  
**Exit condition:** `echo hello` in WSL prints "hello" in the Grid buffer (verified by test)

---

## Workspace Layout

Created inside this repo at `gunter/`:

```
gunter/
├── Cargo.toml              # workspace root
└── crates/
    ├── gunter-core/        # Grid, Cell, Color, CellFlags types
    ├── gunter-term/        # vte::Perform impl → Grid mutations
    └── gunter-app/         # main binary — PTY loop, wsl.exe spawn
```

---

## Crate Responsibilities

### gunter-core

- `grid.rs`: `Cell`, `Grid`, `CellFlags` (bold/italic/underline/blink/inverse), `Color`
- `Grid` API: `new(cols, rows)`, `write_cell(x, y, cell)`, `clear_dirty()`, `cursor_move(x, y)`
- No I/O, no external runtime dependency — pure data types
- Independently testable without PTY or VTE

### gunter-term

- `performer.rs`: `GridPerformer` struct implementing `vte::Perform`
- Translates VTE actions → Grid mutations (print, execute, csi_dispatch, etc.)
- Depends on `gunter-core::Grid`
- Unit tests use `vte::Parser` + `GridPerformer` with hand-crafted ANSI byte sequences

### gunter-app

- `main.rs`: opens PTY via `portable_pty`, spawns `wsl.exe`, reads stdout in loop
- Drives `vte::Parser` + `GridPerformer` per byte
- Prints grid to stdout for headless verification
- No async runtime in Phase 1 (tokio added Phase 2)

## TDD Cycle

Each feature task follows this cycle:

1. Agent writes failing test (test exists, code does not)
2. Agent writes minimal code to make test pass
3. `cargo test` — must be green before commit
4. Commit on feature branch
5. Push feature branch
6. Agent notifies orchestrator via MCP agent mail: `done:<bd-id>`
7. Orchestrator reviews, merges to `develop`, generates HTML report

---

## Git Branch Strategy

```
main          ← stable, tagged releases only (v0.1.0 tag after v0.1 complete)
develop       ← integration target; all features merge here
  feat/v0.1-scaffold   ← workspace Cargo.toml + crate skeletons
  feat/v0.1-grid       ← gunter-core Grid/Cell
  feat/v0.1-term       ← gunter-term VTE performer
  feat/v0.1-app        ← gunter-app PTY loop
```

Worktrees: one per feature branch, created by orchestrator before dispatching subagent.

## Reports

Each feature merge generates `./reports/v0.1.x-<feature>.html` containing:

- Commit hash and branch merged
- Approach rationale (why this vs alternatives)
- How the solution was found / key decisions
- Deviations from SPEC (additions, omissions, interpretations)
- Review flags (things needing human attention)
- Notice flags (non-blocking but worth knowing)

After all issues closed: reviewer agent generates `./reports/v0.1.0-review.html` — full version review.

---

## Orchestrator Responsibilities

1. Create `develop` branch
2. Create beads issues (with dependencies)
3. Create worktrees for each feature branch
4. Dispatch subagents via MCP agent mail
5. Monitor inbox for `done:<id>` signals
6. Merge feature branches to `develop` (resolve conflicts if any)
7. Generate HTML reports per merge
8. After v0.1.0 complete: tag `v0.1.0` on `develop`, spawn reviewer

## Out of Scope for v0.1.0

- Async runtime (tokio) — Phase 2
- GPU rendering — Phase 2
- Keyboard input — Phase 2/3
- Pane splits / tabs — Phase 3
- Socket server — Phase 4
- Config hot-reload — Phase 5
- macOS/Linux native builds

---

## Risk Mitigations

- `portable-pty` ConPTY: test `wsl.exe` in PATH before PTY code — abort if missing
- Workspace Rust edition: pin `edition = "2021"` in all crate Cargo.toml files
- vte API: use `vte = "0.13"` (matches Alacritty reference; check docs.rs for current)
